The big picture

Combat D&D is a small but complete web system: a browser app, an API server, a database, live updates to every screen, sign-in without passwords, and automated builds, deploys and backups. This chapter is the map; every later chapter zooms into one part of it. Click any box.

Only three things are running

The browser app draws the screens and talks to the server. It holds no important state of its own: everything it shows came from the server.

The server is one Spring Boot process in one Docker container on Render. It serves the browser app’s files, answers the API, keeps a live connection open to every screen, and enforces every rule.

The database is Postgres on Neon, the source of truth. If the server restarts, everything is rebuilt from it.

Everything else (GitHub Actions, Render’s build system, the backup job) only runs when something happens: a push, a merge, the nightly timer.

Worth noticing early. The server serves the frontend itself. The React build is copied into the server’s jar, so the site and the API share one address (combat-dnd.onrender.com). No CORS setup, and cookies just work. The cost: changing the UI means redeploying the server. Chapter 8 shows how the Dockerfile does it.

Same fight, different screens

In step 7 the server builds a separate snapshot for each viewer. Flip between them: a player’s browser never even receives an enemy’s HP or a hidden enemy.

    
    
    
    
    The totals follow the same rule: they only count attacks this viewer can see, so the hidden archer’s 3 damage on Lyra shows in the DM’s totals but not the player’s. Otherwise “taken 8” next to only 5 logged damage would give the archer away.

    Three patterns you’ll meet again. The download is a plain link, not a fetch: the browser saves it because of the response header. Permission is checked on the server: hiding the button from players isn’t security. And output is treated as untrusted: names are escaped for Markdown, and CSV cells starting with = are neutralised against CSV injection.
    
    
    
  
    

    



    
  
    
    
    The ideas you’ll meet in every chapter
    
    
    
      
    The server decides everythingThe browser asks and displays. Rules and privacy live in one place, so a modified browser can’t cheat.
    
      
    Events are the truthFights are stored as what happened, not as current numbers.
    
      
    Pure core, impure shellThe rules are pure functions, wrapped by layers that handle locks, SQL and HTTP.
    
      
    Full, filtered snapshotsEvery viewer gets the whole tracker they’re allowed to see. Nothing to merge, nothing to drift.
    
      
    One serverThe lock, cache and live streams live in one process’s memory. Simple, and the first thing to change if the app had to grow (Chapter 9).

    Quick check
    
    
    
      
    Lyra’s player presses Log. When does their own screen show the boss at 21 HP?
    
        
    
        
    The browser never changes the tracker itself (no optimistic updates). The POST only returns the new version number; the picture comes from the stream.
    
      
    Where is the boss’s current HP stored?
    
        
    
        
    The database holds the event log. The server keeps a computed copy in memory and can always rebuild it, which is also how the transcript knows HP at every moment.
    
      
    Why does the server send each viewer the whole tracker instead of just what changed?
    
        
    
        
    A few KB per change is cheap, and a reconnect is just one more snapshot. Diffs would need careful ordering and recovery logic.
    
      
    A player edits the page’s JavaScript to show the transcript button. What happens when they press it?
    
        
    
        
    Hiding a button is a convenience. The permission check happens on the server for every request.
