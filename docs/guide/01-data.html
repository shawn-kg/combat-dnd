Data: Postgres and migrations

Everything that has to survive a restart lives in 12 tables in one Postgres database. They weren’t designed in one go: seven migration files built them up as features arrived, and the seventh fixed what a review turned up. Drag the slider to replay that history, and click any table to look inside.

Why Postgres, and a few choices in the columns

Relational, with real rules. Campaigns own players, characters and encounters; encounters own their events. Postgres stores those links as foreign keys and enforces them, along with checks like “HP can’t be negative”. The database refuses bad data even if the code has a bug.

JSON where it helps. Each event’s details go in a payload column of type jsonb, because the twelve kinds of event have different fields. One table, no schema change per event type.

Neon runs a normal Postgres 18 for us, sleeps when nobody’s using it, and keeps a 6-hour restore window. Locally the same code runs against Postgres in Docker.

Migrations: changing a live database safely

The schema isn’t set up by hand. Each change is a numbered SQL file, and Flyway applies them in order when the app starts:

  1. 1Spring starts and hands the database connection to Flyway before anything else runs.
  2. 2Flyway reads its own table, flyway_schema_history: which versions are applied, and a checksum of each file.
  3. 3It runs any new files in version order, each in a transaction, and records them.
  4. 4If an already-applied file’s checksum no longer matches, it refuses to start.
You’ve met step 4. Early on, V1 was edited after your local database had already run it, and the backend wouldn’t start: “Migration checksum mismatch for migration version 1”. The fix was to wipe the local database (docker compose down -v). On the live database, wiping isn’t an option, which is why the rule is: never edit a migration that has run anywhere; add a new one.

Patterns that keep old data working

Add with a default

V2 adds locked_batch … not null default 0. Existing encounters get 0 at once, so a not null column can be added to a table that already has rows.

Add as optional

V6 adds dndbeyond_url with no default: it’s simply empty for every existing character.

Move data in the same step

V4 creates dm_device and copies every campaign’s existing DM token into it in the same file, so no DM was signed out by the upgrade.

Relax before removing

V4 makes the old dm_token_hash optional instead of dropping it. A later migration can drop it once nothing uses it: the “expand, then contract” pattern.

Two building blocks: indexes and foreign keys

An index is a sorted lookup structure kept beside a table, like the index at the back of a book. Without one, “every encounter in campaign X” means checking every row (a sequential scan). With one, Postgres walks a shallow sorted tree (a B-tree) straight to the matching rows.

Indexes aren’t free: every insert or update also updates each index on the table, and they take disk space. So you add them for lookups you actually make. Postgres builds one automatically for every primary key and unique constraint. It does not build one for a foreign-key column, which is why V7 had to add three.

A multi-column index works for its first column on its own. (encounter_id, seq) also finds “where encounter_id = …” fast, but not “where seq = …”: like a phone book sorted by last name, then first name.

A foreign key is a column holding another row’s id, plus a rule Postgres enforces: that row must exist. character.campaign_id must name a real campaign. It also says what happens when the target is deleted: cascade (delete these rows too), set null (keep them, empty the link), or the default, restrict (refuse the delete while anything still points at it).

Secrets: the database never sees them

    
There are no passwords. Each browser gets a random secret in a cookie, and the database keeps only a fingerprint of it. Make one yourself: this runs in your browser with the same method the server uses.

    

      

        
The cookie (your browser keeps this)

        
32 random bytes, written in URL-safe Base64, like Session.newToken().

        
—

        

      

      
→SHA-256
one way

      

        
The database (keeps only this)

        
Its SHA-256 hash in hex, like Session.hash(), stored in dm_device.token_hash or player.token_hash.

        
—

        
Change one letter of the token and the hash changes completely. There’s no way back from the hash to the token.

      

    

    

      

        
Signing in is: hash the cookie that came with the request, then look for a row with that hash. A match means it’s you. A database leak only reveals hashes, which can’t be turned back into cookies, so nobody can sign in with them.

        
Why SHA-256 and not bcrypt? Slow hashes like bcrypt exist for passwords, because people choose guessable ones and attackers try billions of guesses. Our tokens are 256 random bits: there’s nothing to guess, so a fast hash is the right tool, and every request stays quick.

        
The join code is different. Six characters from a 31-character alphabet (no 0/O or 1/I/L, so it survives being read aloud): 31⁶ ≈ 887 million codes. Guessable in principle, which is why joining is rate-limited (30 tries per address per 10 minutes) and the DM still approves everyone.

Fixed in V7

    
This chapter used to end with four gaps a reviewer would point out. One migration, V7__tidy_up.sql, fixed them all. Move the slider above between V6 and V7 to see each change.

    

      
Missing indexes
encounter and monster_template were looked up by campaign_id with no index. Writing the fix turned up three more: foreign-key columns that cascading deletes have to search (encounter_party.character_id, encounter_enemy.monster_template_id, encounter_npc.npc_id). Five indexes now.

      
The leftover column
campaign.dm_token_hash is dropped: the “contract” half of what V4 started. Safe during a deploy, because the previous version hadn’t used it since V4 either.

      
Portrait links
Every portrait_key is now a real foreign key, and each portrait belongs to its campaign, so deleting a campaign deletes its pictures. Keys that pointed at nothing were cleared first, or adding the constraint would have failed on old local databases.

      
The stale comment
V1 can’t be edited (its checksum is recorded), so the correct description now lives in the database: comment on column character.portrait_key is '…'. See it with \d+ character.

    

    
Expand and contract, again. V7 gives portrait.campaign_id a value for every existing picture, but leaves the column optional. During a deploy the old version keeps serving for a minute while the new one starts, and the old code saves portraits without a campaign. If the column were required, an upload in that minute would fail. A later migration can make it required once only new code is running.

Quick check

    

      
You need a new column on character. What do you do?

        

        
V1 has already run everywhere, so editing it makes Flyway refuse to start (checksum mismatch). Hand changes aren’t recorded and won’t happen on anyone else’s database. A new migration runs once everywhere, in order.

      
Someone steals a copy of the database. Can they sign in as the DM?

        

        
The server hashes whatever cookie arrives and compares hashes. A stolen hash can’t be sent as a cookie, because the server would hash it again and get something different.

      
Two players click the same character at the same instant. What makes sure only one gets it?

        

        
Postgres applies the two updates one after the other; the condition is checked against the latest data. The unique constraint on player_id is a second safety net.

      
You add a column that points at another table, like encounter_enemy.monster_template_id. What does Postgres give you automatically?

        

        
Postgres indexes primary keys and unique columns by itself, nothing else. Without an index on that column, deleting a monster means reading every encounter_enemy row to find the ones to cascade. That’s one of the gaps V7 fixed.

      
Why can’t the AttackLogged event class simply be renamed?

        

        
The type column says AttackLogged for every attack ever logged. A rename needs a mapping from old names (or a migration that rewrites the column).
